# Инструкция: как подключить своё приложение к SSO

Эта инструкция для тех, кто впервель настраивает вход через единый логин (SSO) в своём
приложении. Ничего заранее знать про OAuth2/OIDC не нужно — все термины объясняются по ходу.

Все примеры показаны на вымышленном приложении **hello_sso** — сайт `https://hello-sso.example.com`,
которому нужна кнопка «Войти через SSO».

Адрес самого SSO-сервера в примерах — `https://sso.example.com`. Везде, где встречается этот адрес,
подставляйте адрес вашего реального SSO-сервера (его вам должен был сообщить администратор, либо это
`http://localhost:8080`, если вы запустили SSO у себя локально).

---

## Что такое SSO и что он даёт

SSO (Single Sign-On) — это отдельный сервис, который хранит всех пользователей, пароли, вторую
ступень входа (MFA) и т.д. Вместо того чтобы delать в своём приложении форму логина и таблицу
пользователей самому, вы «отправляете» пользователя войти на SSO, а SSO потом сообщает вашему
приложению: «это пользователь Иван, вот его email, он подтверждён».

Схема на пальцах:

1. Пользователь нажимает «Войти» в hello_sso.
2. hello_sso перенаправляет браузер пользователя на SSO.
3. Пользователь вводит логин/пароль (и код MFA, если включён) на SSO — hello_sso пароль вообще не видит.
4. SSO перенаправляет пользователя обратно в hello_sso вместе с одноразовым кодом.
5. hello_sso «за кулисами» (сервер к серверу) обменивает этот код на токены и узнаёт, кто вошёл.

Это стандарт называется **OAuth 2.0 / OpenID Connect (OIDC)** — SSO реализует именно его, поэтому
подключиться можно почти любой готовой библиотекой (Passport.js, NextAuth, Spring Security OAuth2,
Authlib для Python и т.д.), не изобретая свой код.

---

## Что понадобится перед началом

- Доступ к панели администратора SSO под учётной записью с правами администратора
  (адрес вида `https://sso.example.com/login`).
- Понимание, на каком адресе будет работать ваше приложение (hello_sso), и на какой именно URL внутри
  него должен вернуться пользователь после входа — например `https://hello-sso.example.com/auth/callback`.
  Этот адрес называется **redirect URI**, придумайте и зафиксируйте его заранее.

---

## Шаг 1. Зайти в панель администратора SSO

1. Откройте в браузере `https://sso.example.com/login`.
2. Введите логин/email и пароль администратора SSO.
3. Если включена вторая ступень входа (MFA), введите код из приложения-аутентификатора.
4. После входа вы попадёте в панель администратора — слева будет меню: Users, Roles, Groups,
   **Clients**, LDAP, Identity Providers, Audit, Account.

---

## Шаг 2. Зарегистрировать приложение hello_sso как «клиента» SSO

Каждое приложение, которое хочет входить через SSO, должно быть заранее зарегистрировано —
это называется **OAuth-клиент**. Без этого SSO не будет знать о существовании hello_sso и откажет
в авторизации.

1. В левом меню откройте **Clients**.
2. Нажмите кнопку **«New client»** (справа сверху).
3. Откроется форма. Заполните поля:

   | Поле | Что это | Что вписать для hello_sso |
   | --- | --- | --- |
   | **client_id** | Уникальный идентификатор приложения (латиница, без пробелов) | `hello_sso` |
   | **Name** | Человекочитаемое название, видно в списке клиентов и на экране согласия | `Hello SSO Demo App` |
   | **Type** | `confidential` — если у приложения есть свой сервер, который может хранить секрет (обычный backend-сайт); `public` — если это SPA/мобильное приложение без сервера, где секрет спрятать негде | `confidential` |
   | **Allowed scopes** | Какие данные о пользователе приложению разрешено запрашивать, через пробел | `openid profile email` |
   | **Redirect URIs** | Куда SSO разрешено перенаправлять пользователя после входа — ровно тот адрес, что будет запрашивать приложение, посимвольно | `https://hello-sso.example.com/auth/callback` |
   | **Post-logout redirect URIs** | Куда вернуть пользователя после выхода (необязательно) | `https://hello-sso.example.com/` |
   | **Back-channel logout URI** | Технический адрес, на который SSO сам «постучится», если нужно разлогинить пользователя без его участия (необязательно, для продвинутых сценариев) | оставить пустым |
   | **Skip consent** | Если включено — пользователь не увидит экран «hello_sso запрашивает доступ к...» и вход пройдёт сразу. Включайте только для доверенных собственных приложений | оставить выключенным для начала |
   | **Enabled** | Клиент активен | включено |

4. Нажмите **Save**.
5. Появится жёлтое сообщение с **client_secret** — это пароль приложения, он показывается **только
   один раз**. Скопируйте его прямо сейчас и сохраните в надёжном месте (менеджер секретов, `.env`
   файл сервера hello_sso и т.п.). Если вы его потеряете — на странице клиента есть кнопка
   «Rotate secret», которая выдаст новый (старый после этого перестанет работать).

   > **Важно:** client_secret — это как пароль от приложения. Никогда не кладите его в код, который
   > отправляется в браузер (JavaScript на фронтенде), не публикуйте в git-репозитории. Он нужен
   > только серверной части hello_sso.

После сохранения у вас есть три значения, которые понадобятся дальше:

- `client_id` = `hello_sso`
- `client_secret` = *(то, что показали один раз — держите в секрете)*
- `redirect_uri` = `https://hello-sso.example.com/auth/callback`

## Шаг 3. Что означают scopes (области доступа)

При регистрации мы указали `openid profile email` — это то, какие данные о пользователе может
запросить приложение:

- `openid` — обязателен всегда, включает сам механизм OIDC и выдачу «удостоверения личности» (ID Token).
- `profile` — имя пользователя (`preferred_username`) и источник учётной записи.
- `email` — email пользователя.

Приложение не сможет запросить больше, чем разрешено в **Allowed scopes** клиента — если попробует,
SSO ответит ошибкой `invalid_scope`.

## Шаг 4. Как это подключить в самом приложении (для разработчика hello_sso)

Дальше — то, что должен сделать backend-разработчик hello_sso. Если у вас есть готовый OAuth2/OIDC
модуль в вашем фреймворке (Passport, NextAuth.js, Spring Security, Authlib, `oauth2-proxy` и т.п.) —
проще всего сконфигурировать именно его следующими значениями, а шаги 4a–4f ниже не делать руками:

- **Discovery URL / Issuer**: `https://sso.example.com`
- **Authorization endpoint**: `https://sso.example.com/oauth2/authorize`
- **Token endpoint**: `https://sso.example.com/oauth2/token`
- **UserInfo endpoint**: `https://sso.example.com/oauth2/userinfo`
- **JWKS URL**: `https://sso.example.com/.well-known/jwks.json`
- **Client ID / Client Secret**: значения из Шага 2
- **Redirect URI**: `https://hello-sso.example.com/auth/callback`

Большинство библиотек умеют сами прочитать всё необходимое по одному адресу — «Discovery document»:

```
GET https://sso.example.com/.well-known/openid-configuration
```

Если готового модуля нет и вы делаете это вручную — вот пошагово, что должен делать код hello_sso.

### 4a. Кнопка «Войти через SSO»

На кнопке — ссылка, которая ведёт пользователя на SSO с параметрами запроса:

```
https://sso.example.com/oauth2/authorize
  ?response_type=code
  &client_id=hello_sso
  &redirect_uri=https://hello-sso.example.com/auth/callback
  &scope=openid profile email
  &state=СЛУЧАЙНАЯ_СТРОКА_ДЛЯ_ЗАЩИТЫ_ОТ_CSRF
```

`state` — случайная строка, которую генерирует hello_sso перед редиректом и сохраняет (например, в
сессии пользователя). После возврата с SSO нужно свериться, что `state` совпадает — это защищает
от подделки запроса.

### 4b. Пользователь входит на SSO

Пользователь вводит логин/пароль (и MFA-код, если включён) на странице SSO. hello_sso в этом
не участвует и пароль не видит.

### 4c. Экран согласия (если Skip consent выключен)

Если для клиента не включён «Skip consent», при первом входе пользователь увидит страницу вида
«hello_sso запрашивает доступ к: профиль, email» и должен нажать «Разрешить». В следующий раз это
уже не спросится (разрешение запоминается).

### 4d. SSO перенаправляет пользователя обратно в hello_sso

Браузер попадает на ваш `redirect_uri` с кодом в адресной строке:

```
https://hello-sso.example.com/auth/callback?code=ОДНОРАЗОВЫЙ_КОД&state=ТА_ЖЕ_СТРОКА
```

Сервер hello_sso должен: (1) проверить, что `state` совпадает с сохранённым; (2) забрать `code`.

### 4e. Сервер hello_sso обменивает код на токены

Это запрос сервер-сервер (браузер пользователя тут не участвует), с использованием `client_secret`:

```bash
curl -X POST https://sso.example.com/oauth2/token \
  -d grant_type=authorization_code \
  -d code=ОДНОРАЗОВЫЙ_КОД \
  -d redirect_uri=https://hello-sso.example.com/auth/callback \
  -d client_id=hello_sso \
  -d client_secret=ВАШ_CLIENT_SECRET
```

Ответ:

```json
{
  "access_token": "...",
  "id_token": "...",
  "refresh_token": "...",
  "token_type": "Bearer",
  "expires_in": 900
}
```

- **`id_token`** — подписанный SSO «пропуск», в нём уже есть данные о пользователе (id, email,
  время входа). Это то, что обычно используют, чтобы завести пользователю сессию в hello_sso.
- **`access_token`** — токен для обращения к API SSO от имени пользователя (например, `/oauth2/userinfo`).
- **`refresh_token`** — «долгоживущий» токен, чтобы получать новый `access_token`, не заставляя
  пользователя логиниться заново (см. Шаг 5).

### 4f. Получить данные о пользователе

Либо распарсить `id_token` (это стандартный JWT, для проверки подписи используйте JWKS-адрес
`https://sso.example.com/.well-known/jwks.json` — большинство JWT-библиотек делают это сами по
Discovery URL), либо запросить напрямую:

```bash
curl https://sso.example.com/oauth2/userinfo \
  -H "Authorization: Bearer ВАШ_ACCESS_TOKEN"
```

Ответ (в зависимости от выданных scopes):

```json
{
  "sub": "b3f1...-уникальный id пользователя",
  "email": "ivan@example.com",
  "preferred_username": "ivan",
  "source": "local"
}
```

На этом этапе hello_sso считает пользователя вошедшим и обычно заводит собственную сессию/куку по
`sub` (уникальный ID пользователя) из ответа.

## Шаг 5. Обновление токена без повторного входа (refresh_token)

Когда `access_token` истёк (по умолчанию — через 15 минут), не нужно снова гнать пользователя на
страницу входа. Обменяйте `refresh_token` на новую пару токенов:

```bash
curl -X POST https://sso.example.com/oauth2/token \
  -d grant_type=refresh_token \
  -d refresh_token=ВАШ_REFRESH_TOKEN \
  -d client_id=hello_sso \
  -d client_secret=ВАШ_CLIENT_SECRET
```

Ответ содержит новый `access_token` и **новый** `refresh_token` — старый `refresh_token` после этого
использовать больше нельзя (он одноразовый и после обмена аннулируется), поэтому всегда сохраняйте
последний полученный.

---

## Шаг 6. Выход пользователя (logout)

Чтобы разлогинить пользователя и на стороне SSO (а не только удалить куку hello_sso), отправьте
браузер на:

```
https://sso.example.com/oauth2/logout
  ?id_token_hint=ПОСЛЕДНИЙ_ПОЛУЧЕННЫЙ_ID_TOKEN
  &post_logout_redirect_uri=https://hello-sso.example.com/
```

`post_logout_redirect_uri` обязательно должен быть одним из адресов, указанных в поле
**Post-logout redirect URIs** клиента (Шаг 2), иначе SSO откажется на него перенаправлять.

## Публичные приложения (SPA, мобильные) — PKCE

Если hello_sso — это чисто фронтенд-приложение без своего сервера (например, SPA на React/Vue) или
мобильное приложение, у которого негде спрятать `client_secret`, зарегистрируйте клиента с типом
**public** (Шаг 2) и добавьте в запрос авторизации PKCE — дополнительную защиту, заменяющую секрет:

1. Сгенерируйте на клиенте случайную строку `code_verifier` (43–128 символов).
2. Посчитайте `code_challenge = BASE64URL(SHA256(code_verifier))`.
3. В ссылке из Шага 4a добавьте `&code_challenge=...&code_challenge_method=S256`.
4. При обмене кода на токен (Шаг 4e) вместо `client_secret` передайте `code_verifier=...` — по нему
   SSO проверит, что токен запрашивает тот же, кто начинал вход.

Большинство готовых OIDC-библиотек для SPA (например, `oidc-client-ts`) делают PKCE автоматически —
достаточно указать `client_id` и что клиент публичный.

## Быстрая проверка руками (без кода), через curl/Postman

Если просто хочется убедиться, что клиент настроен правильно, до написания кода в hello_sso:

1. Вставьте в браузер ссылку из Шага 4a (с вашими `client_id`/`redirect_uri`).
2. Войдите под тестовым пользователем SSO.
3. После редиректа на `redirect_uri` скопируйте `code` из адресной строки (страница может показать
   ошибку «не найдено» — это нормально, если hello_sso ещё не написан, код всё равно виден в адресе).
4. Выполните curl-запрос из Шага 4e с этим кодом — если всё настроено верно, придёт JSON с токенами.

## Частые ошибки

| Ошибка от SSO | Причина | Как исправить |
| --- | --- | --- |
| `invalid_client` | Неверный `client_id`/`client_secret`, либо клиент не найден или выключен (`Enabled` = нет) | Проверьте значения и что клиент включён в панели администратора |
| `invalid_grant` | Код авторизации/refresh_token истёк, уже использован или не совпадает `redirect_uri` | Пройдите вход заново; убедитесь, что `redirect_uri` в запросе токена совпадает символ-в-символ с тем, что был в запросе авторизации |
| `invalid_scope` | Приложение запросило scope, которого нет в **Allowed scopes** клиента | Добавьте нужный scope в настройках клиента (Шаг 2) |
| `login_required` | У пользователя нет активной сессии на SSO | Это нормально при первом входе — SSO покажет форму логина |
| `consent_required` | Пользователь ещё не подтвердил доступ, а запрос отправлен как «не интерактивный» (без открытия страницы в браузере) | Открывайте ссылку авторизации в обычном браузере, чтобы SSO мог показать экран согласия, либо включите `Skip consent` для доверенного приложения |
| Редирект не срабатывает / «redirect_uri mismatch» | Адрес в запросе не совпадает точь-в-точь (даже слэш на конце важен) с тем, что вписан в **Redirect URIs** клиента | Сверьте адреса посимвольно в панели администратора |

## Коротко: чек-лист для подключения нового приложения

1. Завести OAuth-клиента в панели администратора SSO (**Clients → New client**).
2. Записать `client_id`, `client_secret` (показывается один раз!) и точный `redirect_uri`.
3. Настроить свой фреймворк/библиотеку на использование Discovery URL SSO
   (`https://sso.example.com/.well-known/openid-configuration`) с этими `client_id`/`client_secret`.
4. Проверить вход тестовым пользователем end-to-end: кнопка входа → форма SSO → согласие →
   возврат в приложение → приложение видит email/username пользователя.
5. Настроить выход (`/oauth2/logout`) и обновление токена (`refresh_token`), чтобы пользователя не
   разлогинивало каждые 15 минут.

# План разработки

Файл содержит только ещё не устранённые проблемы и будущие улучшения. Завершённые пункты следует удалять; текущее поведение документируется в `README.md`.

## Критические исправления безопасности

### Исключить раскрытие LDAP bind password через административный API

`GET /api/v1/ldap/providers`, а также ответы создания и обновления провайдера сейчас сериализуют расшифрованный `bind_password`: репозиторий расшифровывает значение, а HTTP-обработчик возвращает доменную модель без очистки секрета.

- Ввести отдельную безопасную модель ответа либо безусловно очищать `BindPassword` на границе HTTP-транспорта.
- Оставить пустое значение пароля в запросе обновления как команду сохранить существующий секрет, не возвращая сам секрет клиенту.
- Добавить handler- и интеграционные тесты, подтверждающие отсутствие секрета в ответах списка, создания, обновления и ошибок.
- Проверить остальные API-модели с обратимо хранимыми секретами на тот же класс утечки.

### Связать состояние внешнего входа с браузером и сделать его одноразовым

Подписанный `state` в broker содержит случайный `nonce`, но не связывается с инициировавшим браузером и не потребляется. Перехваченный или созданный атакующим callback можно передать другому браузеру и навязать ему сессию учётной записи атакующего (login CSRF); подписывание и срок действия сами по себе этого не предотвращают.

- Хранить только хеш одноразового состояния на сервере либо связать его с защищённой `HttpOnly`, `Secure`, `SameSite` cookie браузера.
- Потреблять состояние атомарно при callback и отклонять повторное использование, состояние из другого браузера и истёкшее состояние.
- Не помещать секреты или токены провайдера в состояние и журналы.
- Добавить негативные интеграционные тесты для replay и cross-browser callback.

## Высокий приоритет

### Защитить выдачу OAuth-согласия от CSRF

`POST /oauth2/consent` аутентифицируется напрямую по session cookie, но не проверяет `X-CSRF-Token` и `Origin`. `httpx.Decode` принимает JSON независимо от `Content-Type`, поэтому same-site страница с другого origin может отправить простой запрос с `text/plain`; CORS не отменяет уже выполненную сервером мутацию.

- Применить к выдаче согласия общую cookie-аутентификацию с проверками CSRF и origin.
- Ограничить изменяющие JSON-маршруты ожидаемым `Content-Type` либо явно доказать безопасность другого формата.
- Добавить тесты для отсутствующего/неверного CSRF-токена, чужого `Origin`, `Sec-Fetch-Site: cross-site` и корректного same-origin запроса.

### Завершить интерактивный Authorization Code Flow

`GET /oauth2/authorize` сейчас отвечает JSON с `401 login_required` или `403 consent_required`. Обычный OIDC/OAuth-клиент, открывший authorization endpoint в браузере, не перенаправляется на существующие страницы входа и согласия, поэтому стандартный интерактивный сценарий обрывается.

- После полной проверки `client_id`, точного `redirect_uri` и scope безопасно перенаправлять пользователя на вход или consent с сохранением исходного запроса авторизации.
- После входа/согласия возобновлять запрос без возможности подменить клиент, URI, scope, `state`, `nonce` или PKCE-параметры.
- Протокольные ошибки перенаправлять клиенту только после подтверждения зарегистрированного `redirect_uri`; иначе показывать локальную ошибку.
- Покрыть интеграционным тестом полный браузерный цикл: authorize → login → consent → callback, включая отказ пользователя.

### Согласовать self-service API с cookie-сессиями SPA

SPA после входа хранит только cookie, а `GET /api/v1/auth/me` и маршруты управления сессиями защищены исключительно `BearerAuth`. После перезагрузки `auth.restore()` получает `401`, сбрасывает пользователя и отправляет его на повторный вход; список и отзыв сессий через браузер также недоступны.

- Использовать общую схему `ProtectedAuth` для self-service маршрутов, сохранив поддержку admin bearer-токенов.
- Для `DELETE` при cookie-аутентификации обязательно сохранить проверки CSRF и origin.
- Добавить интеграционные тесты восстановления SPA по session cookie, управления своими сессиями и немедленного отказа для отозванной/истёкшей сессии.

## Усиление защиты

### Ограничить распределённый перебор учётных данных

Текущие rate limit и блокировка используют ключи «IP + маршрут» и «имя пользователя + IP». Смена IP позволяет продолжать перебор одного имени пользователя без общего для учётной записи ограничения.

- Добавить кластерный лимит или адаптивную задержку по нормализованному хешу имени пользователя, не сохраняя логин в открытом виде в таблице ограничителя.
- Не допустить простого постоянного отказа в обслуживании конкретной учётной записи: определить конечные окна, восстановление и наблюдаемость.
- Унифицировать нормализацию имени между поиском пользователя, аудитом, lockout и rate limit.
- Добавить конкурентные и многопроцессные тесты обхода через разные IP.

## Отложенные протоколы интеграции

Реализовывать только после появления подтверждённого потребителя и согласованных требований:

- SAML 2.0.
- SCIM.
- OAuth 2.0 Token Exchange (RFC 8693).

До реализации определить модель угроз, сценарии, совместимые продукты и критерии приёмки.

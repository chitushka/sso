# План разработки

Файл содержит только ещё не устранённые проблемы и будущие улучшения. Завершённые пункты следует удалять; текущее поведение документируется в `README.md`.

## Высокий приоритет

### Согласовать self-service API с cookie-сессиями SPA

SPA после входа хранит только cookie, а `GET /api/v1/auth/me` и маршруты управления сессиями защищены исключительно `BearerAuth`. После перезагрузки `auth.restore()` получает `401`, сбрасывает пользователя и отправляет его на повторный вход; список и отзыв сессий через браузер также недоступны.

- Использовать общую схему `ProtectedAuth` для self-service маршрутов, сохранив поддержку admin bearer-токенов.
- Для `DELETE` при cookie-аутентификации обязательно сохранить проверки CSRF и origin.
- Добавить интеграционные тесты восстановления SPA по session cookie, управления своими сессиями и немедленного отказа для отозванной/истёкшей сессии.

## Усиление защиты

### Ограничить распределённый перебор учётных данных

Текущие rate limit и блокировка используют ключи «IP + маршрут» и «имя пользователя + IP». Смена IP позволяет продолжать перебор одного имени пользователя без общего для учётной записи ограничения.

- Добавить кластерный лимит или адаптивную задержку по нормализованному хешу имени пользователя, не сохраняя логин в открытом виде в таблице ограничителя.
- Не допустить простого постоянного отказа в обслуживании конкретной учётной записи: определить конечные окна, восстановление и наблюдаемость.
- Унифицировать нормализацию имени между поиском пользователя, аудитом, lockout и rate limit.
- Добавить конкурентные и многопроцессные тесты обхода через разные IP.

## Отложенные протоколы интеграции

Реализовывать только после появления подтверждённого потребителя и согласованных требований:

- SAML 2.0.
- SCIM.
- OAuth 2.0 Token Exchange (RFC 8693).

До реализации определить модель угроз, сценарии, совместимые продукты и критерии приёмки.
